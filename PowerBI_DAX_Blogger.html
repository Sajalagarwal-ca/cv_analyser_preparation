Power BI, End to End — From Data Connection to DAX and a Reusable Date Table

A practitioner's tour of Microsoft Power BI: what it is, how it moves data, the DAX measures that show up in every real report, and a battle-tested Power Query function that spins up a full-featured date table with a single line of M.

Who this is for: Analysts, BI developers, and data engineers who want a single reference that goes from "what is Power BI?" to "what should my measures look like?" — without the marketing gloss.

1 · Power BI in One Paragraph

Power BI is Microsoft's cloud-hosted business analytics platform. It is a family of tools — Power BI Desktop for authoring, the Power BI Service for sharing, Power BI Mobile for consumption, and Power BI Premium for dedicated capacity — that together let you ingest data from almost anywhere, model it, visualize it, and distribute the result. The engine underneath is the same tabular / VertiPaq engine that ships in SQL Server Analysis Services, which is why serious modeling in Power BI feels a lot like modeling in SSAS.

Why teams pick it

  • Real-time analysis via direct connections and scheduled refresh.
  • 100+ built-in data connectors covering files, databases, SaaS, and web services.
  • Custom visuals gallery for anything the standard visuals don't cover.
  • Quick Insights for automated "what's interesting?" scans.
  • On-premises data gateway for secure hybrid connectivity.
  • Modern web stack (HTML5, column-store, cloud, mobile) with monthly feature drops.

The component map (jargon decoder)

  • Power Query — access, search, and transform data. This is the ETL layer.
  • Power Pivot — in-memory tabular modeling and DAX calculations.
  • Power View — the interactive visual layer.
  • Power Map — 3D geo-spatial visualization.
  • Power BI Desktop — the free authoring tool that packages all of the above.
  • Power BI Website / Service — SaaS for sharing dashboards and reports.
  • Power Q&A — natural language querying against the model.
  • Power BI Mobile — iOS, Android, Windows apps for consumption on the go.
  • Data Management Gateway — secure bridge to on-prem sources; owns refresh schedules.

Three-stage architecture

Every Power BI solution — no matter how big — collapses into three stages:

  1. Data Integration — connectors + Power Query pull data in.
  2. Data Processing — the tabular engine models, relates, and stores it in-memory.
  3. Data Presentation — reports, dashboards, apps, and Q&A serve it out.

2 · Data Connections — The Three Modes That Change Everything

Power BI Desktop supports 100+ data sources and growing, but the choice that actually shapes your architecture is not where you connect — it is how. There are three connection modes, and each one trades off freshness, performance, and modeling flexibility.

Aspect Import DirectQuery Live Connection
Behavior ETL — data is downloaded into the .pbix file's VertiPaq store. No data download. Every visual fires a live query to the source. No data download. The report is a thin visualization layer over a remote model.
Supported sources All 100+ sources. SQL Server, Azure SQL DB, Azure Synapse, SAP HANA, Oracle, Teradata (and a growing list). SSAS Tabular & Multidimensional, Power BI datasets.
Data sources per report Unlimited — mashup at will. One. One.
Transformations All Power Query transformations (hundreds). Partial — varies by source; anything must fold to native SQL. None — the model is owned upstream.
Mashup Merge (joins), Append (unions), parameterized queries. Merge, Append — within the single source. None.
Modeling Full — relationships, calculated columns & tables, measures, hierarchies. Limited — calculated columns, measures, column type changes. None — model lives on the server.
When to pick it Best performance, most flexibility, most typical case. Refresh cadence is scheduled. Very large or highly volatile data, or where a single source of truth cannot be duplicated. Enterprise SSAS shops with governed semantic models.
Rule of thumb: Start with Import. Move a table to DirectQuery only when it is too large to fit in memory or too volatile to survive a scheduled refresh. Use Live only when someone else already owns the semantic model.

Common Power Query steps you will actually use

Once you have chosen Import, Power Query is where 60% of a BI developer's time goes. The moves that repeat on every project:

  • Remove rows & columns; rename tables and columns.
  • Change data types to control downstream calculation behavior.
  • Merge (join) and Append (union) queries.
  • Pivot / unpivot columns and group rows.
  • Extract date parts — weekday, month name, hour — from datetime.
  • Identify and fix errors row-by-row.
  • Precisely re-order, add, edit, or delete steps in the query.
  • Drop into R or Python scripts for anything the UI can't do.

3 · Model First — Star Schema Is Still the Answer

Before any DAX, the model has to be right. Power BI's engine is heavily optimized for the star schema: one central fact table (quantitative measurements — sales, quantity, price, cost) surrounded by short-and-wide dimension tables (customer, product, date, geography). Get this shape right and everything downstream — performance, DAX, visuals, drill-through — gets easier.

Star schema pros Star schema cons
  • Simpler joins — fact joins to each dim on one key.
  • Simplified reporting logic: as-of, period-over-period.
  • Feeds OLAP / ROLAP cubes efficiently — the engine loves it.
  • Denormalization weakens data integrity at load time.
  • Less flexible than a 3NF model for open-ended analysis.
  • Many-to-many relationships need bridge tables.
Golden rule: Every date-related question you will ever ask needs a proper Date dimension — never rely on the invisible auto-date/time tables. That is the whole reason section 5 exists.

4 · DAX — The Measures That Ship on Every Real Report

DAX (Data Analysis Expressions) is the formula language of Power BI, Power Pivot, and SSAS Tabular. Instead of covering every function, here are the measures we end up writing in almost every sales / operations model — and the pattern each one teaches.

4.1   Foundation measures

Start with the base facts. Everything else builds on these.

Measure Expression
TotalQuantity SUM(Salestable[Quantity])
TotalSales SUMX(Sales, Sales[SellingPrice] * Sales[Amount])
TotalCost SUMX(Salestable, Salestable[Quantity] * RELATED(Product_Data[Cost]))
TotalProfit [TotalSales] - [TotalCost]
ProfitMargin [TotalProfit] / [TotalSales]

Why SUMX and not SUM? SUMX is an iterator. It walks the fact table row-by-row and evaluates the expression per row before summing. That is exactly what you need when the value depends on two or more columns (price × amount), or when it depends on a related table via RELATED().

4.2   Time-intelligence — last year, parallel period, YoY

Measure Expression
TotalSalesLY CALCULATE([TotalSales], SAMEPERIODLASTYEAR(Datestable[Date]))
TotalSalesLY2 CALCULATE([TotalSales], DATEADD(Datestable[Date], -1, YEAR))
ParallelPeriod CALCULATE([TotalSales], PARALLELPERIOD(Datestable[Date], -1, YEAR))
SalesChange / SalesdifferencevsLY [TotalSales] - [TotalSalesLY]

All three time-intelligence functions need a proper marked Date table — a contiguous, single-column-of-dates-with-no-gaps table. Which is exactly what the function in section 5 produces.

4.3   Cumulative & running totals

Measure Expression
CummulativeSales CALCULATE([TotalSales], FILTER(ALLSELECTED(Datestable[Date]), Datestable[Date] <= MAX(Datestable[Date])))
CummulativeSalesLY CALCULATE([TotalSalesLY], FILTER(ALLSELECTED(Datestable[Date]), Datestable[Date] <= MAX(Datestable[Date])))
RunningTotal30day CALCULATE([TotalSales], FILTER(ALL(Datestable[Date]), Datestable[Date] > MAX(Datestable[Date]) - 30 && Datestable[Date] <= MAX(Datestable[Date])))

The pattern: CALCULATE + FILTER + ALL / ALLSELECTED + MAX(current date in scope). Once you internalize this triangle you can build almost any running-window aggregation.

4.4   Ranking & Top-N

Measure Expression
Profitranking RANKX(ALL(Sales[Category]), [TotalProfit], , DESC)
RanksToShow IF([Profitranking] <= RanksToShow[RanksToShow Value], [TotalProfit], BLANK())
Top10Clients CALCULATE([TotalProfit], FILTER(VALUES(Sales[CustomerCompany]), RANKX(ALL(Sales[CustomerCompany]), [TotalProfit], , DESC) <= 10))

RANKX paired with ALL() to break the filter context is the canonical Top-N recipe. Return BLANK() for out-of-rank rows to keep the visual clean.

4.5   What-if scenarios via parameter tables

Measure Expression
PriceChange Value SELECTEDVALUE('PriceChange'[PriceChange])
DemandChange Value SELECTEDVALUE('DemandChange'[DemandChange])
TotalScenarioSales SUMX(Sales, Sales[Amount] * Sales[SellingPrice] * (1 + PriceChange[PriceChange Value]) * (1 + DemandChange[DemandChange Value]))

Combine a disconnected parameter table + a slicer + SELECTEDVALUE and you have a live what-if lever — no VBA, no re-modeling.

4.6   Customer segmentation & distinct counts

Measure Expression
CustomersPerWeekday DISTINCTCOUNT(Sales[CustomerCompany])
ClassifyCustomers CALCULATE([TotalSales], FILTER(VALUES(Sales[CustomerCompany]), COUNTROWS(FILTER(CustomerClassificationTable, RANKX(ALL(Sales[CustomerCompany]), [TotalSales], , DESC) >= CustomerClassificationTable[Min] && RANKX(ALL(Sales[CustomerCompany]), [TotalSales], , DESC) <= CustomerClassificationTable[Max])) > 0))

ABC / VIP customer buckets in one measure: a classification table with Min / Max rank bounds, and RANKX checked twice inside a nested FILTER. Ugly but powerful.

4.7   Weekday vs. weekend — using variables

TotalSalesonWeekends =
VAR weekends =
    FILTER(Datestable, OR(Datestable[DayInWeek] = 5, Datestable[DayInWeek] = 6))
RETURN
    SUMX(weekends, [TotalSales])

TotalSalesonWeekdays =
VAR weekdays =
    FILTER(Datestable, AND(Datestable[DayInWeek] <> 5, Datestable[DayInWeek] <> 6))
RETURN
    SUMX(weekdays, [TotalSales])

VAR / RETURN makes complex measures readable and faster — the engine evaluates each variable once and caches it. Adopt this style universally.

DAX mental model in one line: Every measure evaluates in a filter context. CALCULATE is the only function that can change that context. Master those two ideas and 90% of DAX makes sense.

5 · The Date Table Function — One M Function, Every Time-Intelligence Measure Just Works

Every DAX time-intelligence function above assumes a proper Date dimension: contiguous dates, no gaps, marked as a date table, joined to your fact via a real relationship. Building that by hand every time is painful. The Power Query function below builds it in seconds.

What the function produces

Given a start date and a fiscal-year-start month, it returns a table with all of these columns computed for you:

Column Example Use
Date2026-08-17Relationship key to fact table.
Year / YearNumber2026Slicers and axes.
QuarterOfYear3Quarterly grouping.
MonthOfYear8Sort-by column for month names.
MonthNameAugustHuman-readable axis.
DayOfMonth17Day-level detail.
DateInt20260817Integer surrogate for fast joins/sorts.
MonthInCalendarAug 2026Trend-line axis labels.
QuarterInCalendarQ3 2026Quarter axis labels.
DayInWeek0–6Weekend / weekday logic (see 4.7).
DayOfWeekNameMondayDay-name slicers.
WeekEnding2026-08-22Weekly rollups without holes.
Week Number33ISO-style week bucketing.
MonthnYear / QuarternYearinteger keysSort-by columns for calendar labels.
ShortYear26Compact axis labels.
FYFY27Fiscal-year label — respects the FYStartMonth parameter.

The function — drop this into Power Query as a Blank Query

let fnDateTable = (StartDate as date, FYStartMonth as number) as table =>
  let
    DayCount = Duration.Days(Duration.From(DateTime.Date(DateTime.LocalNow()) - StartDate)),
    Source = List.Dates(StartDate, DayCount, #duration(1, 0, 0, 0)),
    TableFromList = Table.FromList(Source, Splitter.SplitByNothing()),
    ChangedType = Table.TransformColumnTypes(TableFromList, {{"Column1", type date}}),
    RenamedColumns = Table.RenameColumns(ChangedType, {{"Column1", "Date"}}),
    InsertYear = Table.AddColumn(RenamedColumns, "Year", each Date.Year([Date]), type text),
    InsertYearNumber = Table.AddColumn(RenamedColumns, "YearNumber", each Date.Year([Date])),
    InsertQuarter = Table.AddColumn(InsertYear, "QuarterOfYear", each Date.QuarterOfYear([Date])),
    InsertMonth = Table.AddColumn(InsertQuarter, "MonthOfYear", each Date.Month([Date]), type text),
    InsertDay = Table.AddColumn(InsertMonth, "DayOfMonth", each Date.Day([Date])),
    InsertDayInt = Table.AddColumn(InsertDay, "DateInt",
        each [Year] * 10000 + [MonthOfYear] * 100 + [DayOfMonth]),
    InsertMonthName = Table.AddColumn(InsertDayInt, "MonthName",
        each Date.ToText([Date], "MMMM"), type text),
    InsertCalendarMonth = Table.AddColumn(InsertMonthName, "MonthInCalendar",
        each (try(Text.Range([MonthName], 0, 3)) otherwise [MonthName]) & " " & Number.ToText([Year])),
    InsertCalendarQtr = Table.AddColumn(InsertCalendarMonth, "QuarterInCalendar",
        each "Q" & Number.ToText([QuarterOfYear]) & " " & Number.ToText([Year])),
    InsertDayWeek = Table.AddColumn(InsertCalendarQtr, "DayInWeek",
        each Date.DayOfWeek([Date])),
    InsertDayName = Table.AddColumn(InsertDayWeek, "DayOfWeekName",
        each Date.ToText([Date], "dddd"), type text),
    InsertWeekEnding = Table.AddColumn(InsertDayName, "WeekEnding",
        each Date.EndOfWeek([Date]), type date),
    InsertWeekNumber = Table.AddColumn(InsertWeekEnding, "Week Number",
        each Date.WeekOfYear([Date])),
    InsertMonthnYear = Table.AddColumn(InsertWeekNumber, "MonthnYear",
        each [Year] * 10000 + [MonthOfYear] * 100),
    InsertQuarternYear = Table.AddColumn(InsertMonthnYear, "QuarternYear",
        each [Year] * 10000 + [QuarterOfYear] * 100),
    ChangedType1 = Table.TransformColumnTypes(InsertQuarternYear, {
        {"QuarternYear", Int64.Type}, {"Week Number", Int64.Type},
        {"Year", type text}, {"MonthnYear", Int64.Type}, {"DateInt", Int64.Type},
        {"DayOfMonth", Int64.Type}, {"MonthOfYear", Int64.Type},
        {"QuarterOfYear", Int64.Type}, {"MonthInCalendar", type text},
        {"QuarterInCalendar", type text}, {"DayInWeek", Int64.Type}}),
    InsertShortYear = Table.AddColumn(ChangedType1, "ShortYear",
        each Text.End(Text.From([Year]), 2), type text),
    AddFY = Table.AddColumn(InsertShortYear, "FY",
        each "FY" & (if [MonthOfYear] >= FYStartMonth
                     then Text.From(Number.From([ShortYear]) + 1)
                     else [ShortYear]))
  in
    AddFY
in
  fnDateTable

How to use it (three clicks)

  1. In Power BI Desktop, open Transform Data → New Source → Blank Query.
  2. Open the Advanced Editor, paste the code above, and rename the query to fnDateTable.
  3. Create another Blank Query and invoke it: = fnDateTable(#date(2020,1,1), 4) — that gives you every day from 1 Jan 2020 through today, on an April fiscal year. Rename the result to Datestable.

After you load it — do these three things in DAX

  1. Mark as date table — right-click Datestable → Mark as date table → pick the Date column. This is what activates SAMEPERIODLASTYEAR, DATEADD, PARALLELPERIOD, etc.
  2. Relate the fact table's date column to Datestable[Date] (many-to-one).
  3. Sort-by columns: sort MonthName by MonthOfYear, MonthInCalendar by MonthnYear, and QuarterInCalendar by QuarternYear. Otherwise everything alphabetizes and April sits before January.
Why this function beats "just use CALENDARAUTO": It gives you a fiscal year, weekday indexes, week-ending dates, and integer surrogate keys — none of which CALENDARAUTO produces. And because it's a function, you invoke it with any start date and any fiscal-year start month.

6 · Reporting & Publishing

Once the model and measures are in place, publishing follows the same short path every time:

  1. In Power BI Desktop, click Publish and pick a workspace in the Power BI Service.
  2. Set a scheduled refresh on the dataset (Import mode) or a gateway connection (DirectQuery / on-prem).
  3. Pin visuals from the report to a dashboard for the executive one-pager.
  4. Package related reports and dashboards into a Power BI app for role-based distribution.
  5. Embed in Teams, SharePoint, or a custom web app for the last mile.
